IMPORT RUST AUTOMATIQUE V0.5.0 — PROFIL rust-pure-wrapping-functions-1

API
rust_import.import_rust(source: str | bytes, output_dir=None) renvoie un reçu JSON :
status IMPORTED / REFUSED / INCONCLUSIVE ; reason ; module (ou null) ; inventory ; coverage ; evidence_dir (ou null) ; input_execution=false ; limitations. Une erreur de syntaxe ou de domaine est REFUSED. Une erreur matérielle d'archivage est INCONCLUSIVE. Les fondations arithmétiques V0.5.0 sont identifiées par FOUNDATION_V050.json. BASELINE_V2.json et BASELINE_V041.json restent historiques ; les anciennes versions sont conservées sans modification.
source est le contenu, jamais un chemin à ouvrir. bytes doit décoder en UTF-8 strict. str est encodé en UTF-8 strict. Aucun eval, shell, téléchargement, compilation ou exécution de la source n'est fait par l'importeur.
Sans output_dir, la source UTF-8 admissible est conservée dans le reçu et le modèle ; aucune écriture n'est faite. Avec output_dir, ce chemin doit rester dans V0.5.0 et ne traverser aucun lien ou jonction ; chaque appel crée un dossier rust-import-UUID neuf. source.rs conserve les octets exacts avant parsing, receipt.json conserve le reçu. Une source non UTF-8 est refusée mais ses octets restent archivés si le dossier a été fourni. Sans archive, ces octets invalides ne sont pas recopiés dans le JSON, et source_preserved reste false. Le reçu ne promet pas une sauvegarde sur un disque inaccessible.

GRAMMAIRE ET SÉMANTIQUE ADMISES
Un fichier complet de 1 à 8 fonctions libres, sans autre item. Chaque fonction : [pub] fn nom(param: type, ...) -> type { expression }. 1 à 3 paramètres ; type i32 ou bool. Virgule terminale admise dans paramètres et arguments. Les noms sont des identifiants ASCII de 1 à 80 caractères, début lettre ou souligné, suite lettres/chiffres/souligné ; souligné seul et mots-clés réservés par le profil refusés. Les noms de paramètres sont toujours abaissés en p0, p1, p2, avec correspondance originale conservée.
Expressions : paramètres, constantes true/false, entiers décimaux Int32, signe moins uniquement devant une constante décimale, parenthèses, ! booléen, == != sur valeurs de même type, < <= > >= sur Int32, && || booléens, if condition { expression } else { expression }, else if, appels directs aux fonctions internes. La priorité suit ||, &&, comparaisons, préfixe ! puis accès de méthode postfixe et atomes. Une chaîne de comparaisons sans parenthèses est refusée. Les branches et les opérandes sont tous typés, même s'ils seraient inaccessibles à l'exécution.
return expression, avec ou sans point-virgule terminal, est accepté à la place d'un corps terminal. Il est également accepté dans les branches d'un if lorsque ce if est lui-même en position terminale de la fonction. Aucun retour anticipé n'est effacé dans un argument d'appel, une condition ou un opérande : ces cas sont refusés RETURN_OUTSIDE_TAIL_PROFILE. Une expression ordinaire suivie de ; est refusée car sa valeur Rust serait (). Aucun code après return n'est ignoré.
Les signatures sont collectées avant résolution : appels vers une fonction déclarée plus loin admis. Résolution des noms, arité, types, retours, dépendances et absence de cycles vérifiés. Un appel dont le nom est masqué par un paramètre est refusé. Aucun appel externe ou méthode hors des quatre opérations wrapping déclarées ci-dessous n'est admis. Tous les tokens doivent être consommés ; un second item non pris en charge invalide tout l'import.

ARITHMÉTIQUE INT32 EXPLICITE
Les seules méthodes admises sont receiver.wrapping_add(argument), wrapping_sub(argument), wrapping_mul(argument) et wrapping_neg() ; le receveur et les arguments sont Int32. Une virgule terminale est permise pour un argument unique. Chaînes, appels internes, parenthèses et conditionnelles parenthésées sont typés intégralement. Les AST sont binary/int/op add32|sub32|mul32 et neg32/int/operand. Les résultats sont modulo 2^32, ramenés dans [-2147483648,2147483647].
Le suffixe décimal i32 est admis et doit être collé au nombre. Un nombre utilisé comme receveur doit avoir un type i32 explicite : 2147483647i32.wrapping_add(1). Un receveur conditionnel constitué uniquement de constantes non typées est refusé comme ambigu. Un receveur négatif doit être parenthésé : (-1i32).wrapping_add(2). La forme -1i32.wrapping_add(2) est refusée, car Rust applique la méthode avant le signe moins ; aucun changement silencieux de priorité n’est toléré. Les arguments constants nus restent admis. Le signe moins hors littéral n’est pas ajouté : utiliser wrapping_neg().

HORS PROFIL
Liaisons locales, mutation, arithmétique brute +,-,*, division/modulo, checked/saturating, conversions, boucles, match, effets, références, durées de vie, generics, traits, méthodes générales, modules, use, macros, attributs, unsafe, extern, async, const fn, closures, chaînes/caractères, types autres que i32/bool. Les identifiants Unicode/bruts, le BOM, les littéraux hexadécimaux, suffixés autrement que i32 ou avec séparateurs, et certains espaces Rust autres que espace/tabulation/CR/LF sont refusés. Ces refus décrivent le sous-ensemble de l'atelier ; ils ne prétendent pas que ces syntaxes sont invalides en Rust général.
Commentaires // et /* ... */ imbriqués conservés. Ils n'ont aucun effet dans le modèle. Le texte exact, y compris CRLF et Unicode dans les commentaires, reste conservé.

MODÈLE COMMUN ET PROVENANCE
Schéma mia-module-1, profil pure-int32-bool-wrap-call-1. Unités u0..u7 dans l'ordre source. name et qualified_name conservent le nom Rust ; parameters contient p0..p2. Les appels restent des nœuds call du modèle. Le validateur commun calcule les dépendances et l'ordre topologique ; il dérive les contrats exacts result == expression après expansion bornée des appels.
module_id et provenance.import_id valent rust-<SHA256 des octets UTF-8>. provenance conserve source_text exact, source_sha256, origin.language=rust, le profil et source_map. source_map donne pour chaque fonction son ID, nom original, visibilité pub, signature, paramètres originaux/canoniques et positions de déclaration/corps. L'identité de révision est calculée par le modèle commun. Aucune date, UUID d'archive ou chemin d'archive n'entre dans le modèle : deux imports du même texte produisent le même modèle et la même révision. Les empreintes ne sont pas des signatures.
inventory contient source (texte si décodable, taille, SHA, chemin d'archive éventuel), functions, identifiers, tokens significatifs et segments couvrant aussi commentaires/espaces. Chaque segment possède son texte, start/end en indices de caractères Python et byte_start/byte_end en octets UTF-8, plus line/column/end_line/end_column. Intervalles semi-ouverts, indices de caractères/octets à partir de zéro ; lignes/colonnes à partir de un, LF démarre une ligne et chaque caractère Unicode compte pour une colonne. Les tabulations comptent comme un caractère, pas une largeur d'affichage.
lexing_complete, parsing_complete, lexed_chars et coverage.all_tokens_consumed distinguent un inventaire complet d'une interruption au premier défaut ou à une borne. Les tokens déjà analysés et le texte restent conservés ; une couverture interrompue n'est jamais annoncée complète. IMPORTED signifie toute l'entrée parsée et modèle typé, pas source compilée ni équivalence prouvée. semantic_equivalence reste NOT_TESTED ; site_migrated reste false.

BORNES
Parsing : 512 Kio UTF-8 ; 12 000 tokens significatifs, 24 000 segments ; profondeur de parsing 32 ; commentaires imbriqués 16 ; noms 80 caractères ; 8 fonctions ; 3 paramètres/arguments. Littéraux signés dans [-2147483648,2147483647], texte numérique de 11 chiffres maximum avant conversion. AST typé par fonction : 512 nœuds, profondeur 32. Puis limites existantes du modèle commun : expansion 4096 nœuds/profondeur64 et du cœur mathématique, notamment contrats 4096 caractères/AST512/profondeur24. Une fonction compacte dont l'expansion dépasse ces limites est refusée explicitement.
Archivage/recopie : 2 Mio maximum. Une source UTF-8 entre 512 Kio et 2 Mio peut être conservée mais son parsing est refusé. Au-delà de 2 Mio, ARCHIVE_BOUND_INPUT_NOT_COPIED indique clairement qu'aucune copie complète n'est revendiquée. Les limites sont un domaine d'admission et non une isolation système contre un adversaire contrôlant les fichiers.

CAP AIGLE
Cet adaptateur traduit automatiquement une grammaire et sa sémantique admises ; il ne reconnaît pas seulement des exemples ou une empreinte de projet. Le modèle est le même que pour les autres langages déjà disponibles. Le prochain élargissement doit définir les types, états et effets correspondants avant de les admettre. Une information conservée et une information représentée restent deux constats distincts. Un contre-exemple capable d'invalider ce jalon est une source admise dont l'exécution réelle diverge de son modèle sur une entrée admise, ou un morceau non pris en charge accepté silencieusement.
