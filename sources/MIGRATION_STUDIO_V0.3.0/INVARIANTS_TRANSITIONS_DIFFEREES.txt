INVARIANTS DU STUDIO À ÉTAT — INVENTAIRE POUR JALON ULTÉRIEUR
Statut : proposition et lecture du backend V0.2 livré, pas moteur de transitions réalisé. Le coordinateur a choisi pour V0.3 le noyau de notation ; les transitions restent hors migration de ce jalon.
Source relue : StudioStore.cs dba50f86269d45247c00bcb0705a9709383a7d9d48e41504c5767df86c7aa774, Program.cs c5b53894e1a7b9cdb7b36f28c889982996cad8556764334272a39567a78c4fb9.

Premier modèle d'état proposé : F(S,Commande,Environnement)->(S',Réponse,Effets). S conserve l'état entier, pas seulement le score ; les champs sans représentation restent inventoriés et ne disparaissent jamais. Profil initial possible : Get/ReplaceAnswers/Complete sur une tentative réellement initialisée par C#, snapshot conservé. Puis Start, édition, archive et fournisseur d'identité. Profil fermé ; extraction automatique d'un site arbitraire non revendiquée.
Horloge/GUID/shuffle sont des entrées d'environnement distinctes des règles de notation. Une comparaison qui couple la date fraîche observée en C# à une variable symbolique doit déclarer cette hypothèse ; elle ne valide pas la production de l'horloge. Replay doit conserver strictement ancienne date/id/ordre, même si l'environnement offre de nouvelles valeurs. Persistance réussie/échouée doit rester un effet observable ; une API séparée n'est pas une isolation OS.

Ordre observable à préserver
1. Middleware : vérification hôte local ; pour mutation, origine étrangère403 AVANT JSON_REQUIRED400 ; puis routage et binding strict des DTO. Un modèle de Store seul ne couvre pas cette couche.
2. Start : requestIdUUID puis quizId/révision valides ; normaliserUUID et calculer fingerprint ; chercher reçu existant AVANT quiz courant. Même clé/autre payload ->REQUEST_CONFLICT409 ; même demande ->tentative existante200 sans commit, même si quiz édité/archivé. Seulement ensuite quiz404, révision409, archive409, capacité ; snapshot et tirage ; nouvelle tentative201.
3. Answers : tentative404 ; completed409 AVANT comparaisonrevision ; revision409 ; validation réponses dans leur ordre, puis copie/remplacement entier et revision+1. Un PUT identique sur une nouvelle revision écrit à nouveau : ce n'est pas l'idempotence de Complete. Questions non répondues omises ; answers[] autorisé ; optionIds[] refusé ; doublons et IDs étrangers refusés.
4. Complete : tentative404 ; completed rend reçu existant AVANT revision ou complétude. Sinon revision409, réponses complètes400, puis status/date/revision. Une seconde terminaison ne recrée ni date ni ligne de score.
5. UpdateQuiz : quiz404, revision409, archived409, capacitéhistorique, validation nouveauquiz ; archiver ancienneversion ; nouvelleversion+1. ArchiveQuiz : quiz404, revision409 AVANT replay archived ; archived retourne actuel ; sinon capacitéhistorique, archiveancienquiz, revision+1.
6. Rename : nom1..60 nonblanc validé avant Trim ; compte localId reste stable ; anciennes tentatives gardent le nom capturé.
7. Commit : copie séparée, nouvelle révision globale checked, validation d'état, sérialisation/bornes, écrituretemporaireFlush(true), remplacementatomique avecbackup, puis publication mémoire. Refus/exception avant publication ne doit pas produire succès ; rapprochement des reçus nécessaire après effet incertain.

Informations à préserver
Snapshot : quizId/titre/révision, compteId/nom, questions/options/bonnesréponses/explications, ordre effectivement tiré, barème/seuil/correction. Ni édition ni archive ultérieure ne le réécrit. Réponse publique en cours masque correct/explication ; résultat ne montre détails que si le snapshot l'autorise.
Etat global : révision, compte, quiz courants et archivés, historique des anciennes versions, toutes tentatives et requestId/fingerprint, réponses dans ordre fourni, startedAt/completedAt. Le score est recalculé depuis snapshot/answers ; comparer seulement score final perd ces invariants.
Scores : groupes quiz/révision/barème, nom au démarrage ; tri pourcentage rationnel exact descendant, date ascendante, puisId ordinal. correctCount est égalitédesensembles, indépendant de points partiels.
Stockage : dossier explicite, verrou exclusif du processus pendant toute sa vie, limites32MiB/200quiz/2000versions/2000tentatives, aucun nettoyage silencieux. Etat illisible ou primaireabsentavecbackup refusé ; pendingnonrejoué ; récupération explicite. Un JSON valide modifié manuellement n'a pas d'authentification cryptographique.

Cas discriminants prévus, non lancés pour ce modèle futur
Deux erreurs simultanées pour révéler l'ordre des validations ; replayStart après archive ; Complete terminé avec vieille révision ; Answers terminé avec vieille révision ; même requêteAnswers réappliquée avec révisioncourante ; deux mutations concurrentes même révision avec un seul gagnant ; arrêt aprèscommit avant réponse ; identité des snapshots après édition ; différences aux seuils arrondis ; compte renommé ; reprise aprèsarrêt sans nouvellepartie ; préservation des erreurs et des fichiers.
Une campagne future comparera réponse/statut/codeerreur, état complet avant/après, compteurcommits et effets, sur un dossier neuf. Temps/GUID ne seront pas effacés arbitrairement du comparateur. Toute normalisation devra avoir un contrat explicite et conserver les valeurs brutes.
