ATELIER MODULES ET MATHS → CODE V0.2.0

CARTE ET DEUX PARCOURS
La carte se déplace en glissant et se zoome librement à la molette (25–280 %). Vue globale cadre le schéma. Les détails progressent avec le zoom ; un clic sur une unité choisit sa propriété, un clic sur une cible détaille son contrôle. Les onglets séparent résumé, propriété JSON, mathématiques actuelles, code, journal et preuves complètes. Rien n’est supprimé parce que la vue synthétique le masque.
Le mode « Modules reliés » importe plusieurs fonctions et leurs appels. Le mode « Fonction pure » conserve le parcours séparé V0.1, avec synthèse et preuve conditionnelle facultative. Les sources et brouillons des deux modes sont distincts. Aucun modèle de langage n’est chargé.

IMPORTER UN MODULE C#
Importer une classe C# puis lancer l’extraction. Le source proposé Max2/Max3 est un exemple explicite, pas l’inventaire d’un projet utilisateur. Roslyn analyse le source exact ; le C# fourni n’est jamais exécuté. L’inventaire, les refus et les limites sont conservés. Un import partiel n’est pas accepté silencieusement.
Le périmètre contient une classe de 1 à 8 méthodes statiques pures, int32/bool, avec 1 à 3 paramètres. Les comparaisons, booléens, conditions et appels directs internes résolus sont admis. Récursion, effets, appels externes, boucle, arithmétique générale, objets et accès aux fichiers ne le sont pas. Int32 signifie entier signé sur 32 bits.
« Charger le module dans l’atelier » est une action explicite. Chaque unité conserve son identifiant et ses noms source ; les flèches pleines montrent les appels, les traits pointillés l’appartenance au module. Le modèle porte le source, son empreinte, la référence d’import, les contrats et la provenance. Une table de noms cibles ne garantit pas la compatibilité d’une API HTTP ou binaire.

RÉVISER UNE PROPRIÉTÉ
Choisir une unité, puis modifier sa Propriété JSON. parameters décrit les entrées, precondition les entrées admises et postcondition relie result aux paramètres. Exemple maximum : result >= a and result >= b and (result == a or result == b). Pour un minimum, remplacer les deux >= par <=. Aucun programme candidat n’est fourni au synthétiseur dans cet exemple.
Le JSON est un brouillon : le graphe et les mathématiques actuelles représentent toujours la révision chargée. Donner une intention puis cliquer « Créer cette révision ». La synthèse bornée recherche un nouveau corps sans changer la signature. Un succès crée une révision avec parent, ancienne/nouvelle identité et dépendants affectés. Il ne déclare pas l’ancien et le nouveau comportement équivalents.
Les contrats des appelants restent inchangés. Remplacer Max2 par Min2 peut donc rompre le contrat de Max3 ; « Générer et vérifier le module » doit montrer ce contre-exemple. Corriger ensuite les propriétés voulues est une décision explicite. Un échec conserve le module et le brouillon. Les brouillons sont mémorisés par module/révision/unité, y compris quand on change de sélection ou de mode. Recharger la propriété de l’unité remplace explicitement son brouillon par le contrat actuel.
La génération refuse les brouillons non appliqués. Choisir Python, C# et/ou Rust et une préférence explicite ou auto. Les sources produites contiennent de vrais appels entre les unités. Chaque cible affiche son statut de compilation, d’exécution et de contrôle des unités. Auto explique son choix selon ces résultats ; il ne choisit pas un meilleur langage universel.

GAME EDITOR · QCM LOCAL
Le bouton « Game Editor · QCM local » ouvre explicitement le lanceur local fixe launch_site.py. Aucune URL ni chemin arbitraire n’est exécuté. Tant que ce lanceur reste actif, un second clic n’en démarre pas un autre. Le lanceur prépare le Studio ASP.NET Core MVC : compte local unique, QCM configurables à réponses uniques ou multiples, parties et scores persistants. Il gère son serveur sur l’interface locale uniquement. Fermer sa fenêtre de contrôle arrête ses serveurs ; fermer l’atelier n’arrête pas ce lanceur indépendant.
Le statut « Lanceur démarré » ne signifie pas que la compilation, les contrôles, les serveurs ou la migration sont réussis. Ces résultats appartiennent au lanceur et à ses preuves. Le Studio avec état n’est pas traduit par l’atelier de fonctions pures. Le petit QCM de référence et son adaptateur Rust restent un prototype séparé ; aucune migration du Studio n’est revendiquée. La préparation ne se lance jamais au démarrage de l’atelier. Les journaux de lancement se trouvent sous local/site-launches/.

ÉTATS, HISTORIQUE ET PREUVES
Les éditeurs sont verrouillés pendant l’opération. Après retour, la propriété d’une unité peut être modifiée comme brouillon ; le résultat reste lié à la révision archivée. La fenêtre d’import rattache le résultat au source exact et conserve un source non envoyé lors de sa fermeture/réouverture. En mode fonction, « Modifier / nouvel essai » déverrouille les entrées et retire le résultat de l’affichage, tout en conservant son archive.
L’historique est en lecture seule et ne relance rien. Une archive incomplète ou dont les empreintes ne concordent pas reste non vérifiée ; les commandes du module sélectionné sont alors désactivées. Une lecture ancienne ne remplace pas le résultat d’une commande terminée depuis cette lecture. SHA-256 détecte une incohérence locale, pas un adversaire réécrivant toute l’archive.
Chaque demande reçoit un dossier unique local/requests/request-... avec entrées exactes et réponse. Les rapports pipeline/import se trouvent dessous, dans proofs/. Les rapports relient également les fichiers d’exécution conservés dans les dossiers courts runtime/. Le parcours historique de fonction conserve aussi les certificats sous runtime/P-... et les exécutions sous runtime/R-... . Toutes les preuves, réponses, tentatives, sources, inventaires, refus et échecs restent accessibles ; aucun nettoyage automatique.
Les délais UI sont bornés : import module 120 s, génération module 120 s, révision 60 s ; fonction sans preuve 90 s, avec preuve 360 s, import fonction 120 s. Le statut d’activité indique seulement l’opération observée ; il n’invente aucune progression interne. Un dépassement devient INCONCLUSIVE, avec résultat incertain et preuves partielles conservées, sans rejeu automatique.
Fermer l’atelier attend l’archivage de l’opération en cours. Au prochain lancement, aucune expérience ne reprend automatiquement. Zoom, position, sources et brouillons (même JSON incomplet) sont restaurés. Le modèle restauré est revalidé ; les résultats sont dans l’historique et ne sont pas recréés par la restauration d’un brouillon.

PORTÉE DES RÉSULTATS
GENERATED indique des sources produites ; TESTED_FINITE indique des contrôles finis. NON_COMPILE n’est jamais présenté comme compilation réussie. COUNTEREXAMPLE signifie qu’un cas contredit le comportement ou le contrat attendu. Un module reste NOT_PROVED_MODULE : aucune preuve universelle du module dans ce parcours. La preuve Lean conditionnelle du mode fonction reste distincte et ne prouve ni tous les compilateurs ni une équivalence générale C#–Rust.
Une recherche bornée qui échoue ne prouve pas une impossibilité. Des tests finis ne prouvent pas tous les Int32. Les routes, bases de données, authentification, effets, état et comportements navigateur d’un site arbitraire ne sont pas reconstruits par l’importateur pur. Le dossier V0.1 est conservé séparément.
