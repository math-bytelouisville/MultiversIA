BACKENDS DE MODULES PURS — V0.2.0
15 novembre 2026. Génération avec appels réels, exécution des unités et traces de contrats.

API ET IDENTITÉS
emit_module(module, language) valide le modèle, émet chaque unité et conserve les appels directs dans Python, C# et Rust. Il n’insère pas le corps des dépendances à la place des appels. Les symboles cibles sont f0/f1… ou F0/F1… dans MiaModule pour C#. unit_mapping conserve id, nom source, nom qualifié et correspondance paramètres source/p0… avec types. module_id et revision_id lient chaque artefact au modèle normalisé exact. La table ne promet pas une API binaire, un serveur HTTP ou la reconstruction d’un framework.
validate_module_generated régénère l’artefact et compare tous les champs contractuels avant tout processus. Source fournie altérée, mauvaise correspondance d’unités ou révision modifiée : REFUSED sans exécution. Les chaînes de provenance et sources C# collées ne sont pas exécutées.

VÉRIFICATION INDÉPENDANTE ET COMPOSITION
L’oracle parcourt directement l’IR avec appels et nouvelles portées de paramètres. Il n’appelle ni module_model.evaluate_unit ni module_model.inline_unit. Les noms des paramètres peuvent se répéter entre fonctions sans capturer ceux de l’appelant. Il évalue arguments et branches selon le profil pur, puis compare chaque sortie réelle au résultat attendu. Parser des contrats et normalisation des types restent partagés : l’indépendance n’est pas absolue.
Le harness invoque toutes les unités du module complet. Python est exécuté ; C# et Rust sont compilés puis exécutés quand leurs outils sont admis. Chaque ligne de résultat contient l’id de l’unité, sa valeur strictement typée et sa position dans le plan ; une mauvaise attribution, un nombre de lignes incohérent ou une valeur hors Int32 devient FAILED.
Les contrats sont vérifiés séparément de la comparaison au modèle. Le changement volontaire Max2→Min2 peut produire un code conforme au nouveau modèle tout en violant l’ancien contrat de Max3 : le rapport porte COUNTEREXAMPLE, avec les cas de l’appelant.
Depuis chaque entrée racine dont la précondition est vraie, l’oracle contrôle aussi les préconditions des fonctions appelées. Une violation contient kind=CALL_PRECONDITION_VIOLATION, caller, callee, arguments, call_stack et règle violée. Elle reste un contre-exemple même si le résultat final respecte par hasard la postcondition du caller. Les appels d’une racine hors précondition ne réfutent pas son contrat. Une unité seule sous précondition False reste INCONCLUSIVE faute de témoin.
Les traces d’appel proviennent de l’oracle du modèle, pas d’une instrumentation du binaire. La correspondance au code est vérifiée sur les sorties finies ; aucune preuve générale de cette correspondance ni des préconditions d’appel n’est annoncée.

BORNES ET STATUTS
Au plus 512 entrées par unité, jusqu’à huit unités. Échantillons Int32 avec bornes, petites valeurs et voisins des constantes ; booléens False/True. Si le produit dépasse le plafond, la sélection est déterministe et bornée. Il ne s’agit pas d’un parcours exhaustif Int32.
Oracle : deux fenêtres de quinze secondes, l’une pour préparer les cas, l’autre pour vérifier les postconditions des valeurs exécutées. La compilation et l’exécution ne consomment pas ces fenêtres. Le compteur cumulé de deux millions de visites reste commun aux deux phases ; profondeur d’évaluation limitée à 64. Compilation 30 s, exécution 10 s, aucune attente sans borne du processus. Ce sont des contrôles applicatifs, pas une sandbox OS ou un plafond global de RAM.
L’agrégation ne supprime aucune unité : FAILED pour différence de comportement ou sortie mal formée ; COUNTEREXAMPLE pour postcondition ou précondition d’appel violée ; INCONCLUSIVE pour unité sans témoin, timeout, budget oracle ou changement d’outil/source ; TESTED_FINITE seulement si chaque unité dispose de contrôles finis réussis. NON_COMPILE garde les unités et cas planifiés avec zéro exécution. formal_scope reste NOT_PROVED_MODULE.

ARCHIVES ET CHEMINS WINDOWS
Chaque validation possède un dossier neuf module-validation-UUID contenant modèle exact avec provenance, artefact, cases.json, sorties des processus et report.json. Les sources et harness utilisent LF ; leurs octets sont contrôlés avant et après exécution. La compilation utilise un dossier court unique runtime/M-UUID pour éviter les échecs MAX_PATH observés dans V0.1. Les deux copies, les exécutables et sorties restent conservés ; les rapports relient les dossiers et leurs empreintes. Aucun résultat précédent n’est écrasé.

RUST LOCAL AU PROJET
Le coordinateur a préparé rustc/rust-std/rust-mingw 1.100.0 GNU dans toolchains/rust/install à partir de composants officiels et vérifié leurs SHA-256. La qualification initiale portait sur un petit programme Int32 ; elle ne suffisait pas à qualifier les modules. Les essais de ce backend ajoutent de vraies compilations et exécutions des modules, dans le périmètre décrit ci-dessous.
Le backend ne télécharge rien. Si toolchains/rust/manifest.json existe, il exige schema_version=mia-rust-toolchain-1, status=QUALIFIED_LOCAL et une qualification COMPILED_AND_EXECUTED. Il contrôle le type JSON, le confinement des chemins, l’inventaire complet des fichiers installés et leurs empreintes, l’identité de rustc et du linker. Un registre présent mais invalide est refusé ; il ne déclenche pas un repli silencieux.
Le profil GNU admis contient exactement deux options -C : linker=<sysroot>/lib/rustlib/x86_64-pc-windows-gnu/bin/self-contained/x86_64-w64-mingw32-gcc.exe et link-self-contained=yes. Le PATH du seul processus enfant reçoit les deux dossiers qualifiés self-contained et sysroot/bin ; os.environ et le PATH global restent inchangés. Les fichiers inventoriés et le manifeste sont hachés de nouveau avant et après exécution. Les dépendances système de Windows ne sont pas attestées par cet inventaire local. Les hashes assurent une cohérence locale, pas une signature contre un tiers réécrivant tous les fichiers.
Sans registre, les outils déjà présents peuvent être détectés ; l’absence d’un compilateur reste NON_COMPILE. L’ancienne API de fonctions V0.1 copiée reste distincte : le registre portable a été branché sur le nouveau parcours modules.
Sources officielles consultées avant préparation :
Rust Forge, distributions autonomes et cible GNU : https://forge.rust-lang.org/infra/other-installation-methods.html
Rustc book, prérequis Windows GNU : https://doc.rust-lang.org/rustc/platform-support/windows-gnu.html
Les choix locaux exacts, composants et hashes se trouvent dans toolchains/rust/download-plan.json et manifest.json, avec les essais du coordinateur. La réussite du GCC fourni a été constatée ; aucune disponibilité générale de tous projets Rust n’en découle.
