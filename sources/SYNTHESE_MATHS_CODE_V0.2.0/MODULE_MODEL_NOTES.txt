MODÈLE DE MODULES PURS — V0.2.0
15 novembre 2026. Source, types, appels et révisions ; aucune exécution du C# fourni.

API
validate_module(module) rend une nouvelle structure détachée avec revision_id, dependencies, topological_order et coverage. ValueError/TypeError signalent les refus. inline_unit rend un AST pur compatible avec le noyau courant. unit_spec rend les seuls champs publics mia-math-spec-1. evaluate_unit contrôle strictement la liste d’entrées et les types bool/Int32, puis évalue l’AST pur. revise_unit rend REVISED, REFUSED ou INCONCLUSIVE, sans modifier son entrée.
Le modèle suit CONTRAT_MODULES.txt : une à huit unités, identités u0..uN contiguës, paramètres ASCII du noyau (un à trois, result réservé), retours int/bool. Les noms publics et noms qualifiés sont conservés même si les cibles émettent des symboles canoniques. Les noms qualifiés du modèle doivent être uniques. La table de symboles ne restaure pas une API binaire ou HTTP.

VALIDATION ET PORTÉE
Chaque nœud, y compris une branche conditionnelle jamais prise, est contrôlé. Les appels portent un id interne, une arité et des types exacts ; aucune cible externe, récursion directe ou indirecte n’est admise. L’ordre topologique place les dépendances avant leurs appelants. L’inlining évalue les expressions d’arguments dans la portée de l’appelant, puis les substitue simultanément dans la portée du appelé ; réutiliser les mêmes noms de paramètres ne les capture pas.
Les expressions sont totales et sans effet dans ce profil. L’inlining peut dupliquer leur calcul ; cela ne serait pas fidèle pour un futur profil à effets, qui devra avoir une autre sémantique.
La couverture affirme uniquement que toutes les unités DÉCLARÉES sont typées. Le modèle seul ne peut prouver qu’un extracteur a inventorié toutes les unités du fichier d’origine. source_inventory_complete reste NOT_ESTABLISHED_BY_MODEL_ALONE ; l’importeur doit établir son propre inventaire. formal_scope reste NOT_PROVED_MODULE et site_migrated reste false.

BORNES EXPLICITES
Source d’origine : 512 Kio UTF-8 maximum, conservée exactement (y compris CRLF). Objet JSON complet : 2 Mio sérialisés, 50 000 valeurs/clés visitées, profondeur 80 ; cycles, objets non JSON, NaN/inf et entiers de métadonnées dépassant 128 bits sont refusés. Aucun chemin ou texte de provenance n’est ouvert ou exécuté.
Corps de chaque unité : 512 nœuds et profondeur 32. Expansion : au plus 4096 nœuds construits, profondeur 64 et 16384 opérations internes ; les expressions temporaires d’arguments comptent aussi dans le coût. C’est une borne conservatrice sur le travail, non une promesse d’admettre tout AST final de 4096 nœuds.
Le noyau V0.1 copié reste inchangé : son AST pur est limité à 512 nœuds/profondeur 32 et ses propriétés à 4096 caractères, AST Python 512 nœuds, conversion profondeur 24. Après expansion, ses contrôles peuvent donc refuser un module plus tôt avec INLINE_CORE_LIMIT_OR_TYPE ou UNIT_CONTRACT_INVALID. Ces refus sont assumés et coordonnés avec les autres modules. Aucun agrandissement silencieux de la grammaire n’a été effectué.

CONTRATS ET RÉVISION
Si contract est null, un contrat exact result == expression est généré à partir du corps initial entièrement développé, sous précondition True. Un contrat fourni est reparsé dans la DSL existante ; il n’est pas supposé satisfait simplement parce qu’il est bien typé. Le normaliseur contrôle les structures, pas la validité universelle des propriétés.
revise_unit demande au synthétiseur borné une nouvelle expression depuis la propriété proposée, avec la même signature. Une réussite conserve module_id, ids des unités, source d’origine et provenance ; parent_revision_id pointe sur l’ancienne révision. Le corps et le contrat de l’unité choisie changent. Les corps ET CONTRATS des appelants restent inchangés. Ainsi, changer Max2 en Min2 conserve un témoin permettant au backend de constater que Max3 ne respecte plus son ancien contrat. REVISED ne signifie donc pas module qualifié.
Le rapport change contient old_revision_id/new_revision_id, old_unit_sha256/new_unit_sha256, affected_dependents transitifs, validation_required, intent, caller_contracts_preserved et equivalence_claimed=false. La comparaison d’exécution et de contrats par les contrôleurs indépendants reste obligatoire avant toute annonce de validation. Un refus, une propriété contradictoire ou un budget épuisé laisse l’ancien modèle intact.

PROVENANCE ET EMPREINTES
Les champs source_text, source_sha256 et import_id de provenance sont requis ; le hash SHA-256 est vérifié contre les octets UTF-8 exacts du texte. Les autres champs JSON bornés sont conservés, notamment origin, limitations et evidence_dir. Ils ne constituent pas une autorisation d’accès.
revision_id est SHA-256 des champs sources normalisés, contrats générés compris, via JSON trié par clés, sans espaces, ensure_ascii=False et allow_nan=False. Les vues dependencies/topological_order/coverage et revision_id lui-même n’entrent pas dans ce calcul. Les vues reçues sont recalculées. Une empreinte revision_id fournie incorrecte est refusée, jamais remplacée silencieusement.
Ces empreintes détectent une modification par rapport à l’identité fournie ; elles ne sont ni signatures, ni attestation d’un import fidèle, ni preuve que le parent existe. Un tiers capable de refaire toutes les empreintes peut produire un autre modèle. L’archive et sa chaîne de provenance doivent être contrôlées au niveau du pipeline. Le module ne lit ni n’écrit d’archives ; l’immuabilité de son API signifie absence de mutation d’entrée et nouvelles identités de contenu.

CAP AIGLE
Ce jalon ajoute les identités, appels, contrats persistants et provenance API nécessaires au premier module pur. Il ne représente toujours pas état, stockage, HTTP, erreurs, temps, concurrence ou rendu. Le cas qui invaliderait une revendication trop large est déjà concret : une fonction modifiée peut être correcte sous son nouveau contrat tout en cassant l’ancien contrat d’un appelant. Toute vue globale doit montrer ce contre-exemple, au lieu d’annoncer un succès à partir de la seule fonction éditée.
